# 通用智能体规则：上下文写入与记忆管理

## 目标

让智能体在每次任务完成后沉淀可复用的项目知识，使后续任务能够快速恢复项目状态，同时避免把完整对话、临时推理和重复流水账不断堆进上下文。

本规则适用于功能开发、数据处理、设计修改、问题排查、文档维护和部署工作。

## 一、事实来源优先级

记忆文档不是第二套代码库。遇到冲突时，按以下顺序确认事实：

1. 当前代码、配置、数据库结构和可复现的运行结果；
2. Git 历史、变更记录和测试结果；
3. 已确认的架构/决策文档；
4. 工作日志和任务摘要；
5. 对话中的未验证陈述。

如果记忆与代码冲突，先以代码和验证结果为准，再更新或标记过时的记忆；不得为了让记忆看起来一致而修改真实项目行为。

## 二、记忆分层

### 1. 长期事实（Stable）

记录项目目标、边界、技术栈、目录职责、数据流、外部依赖、工程约束、领域模型和命名约定。

### 2. 决策记录（Decision）

记录会影响未来工作的选择，包括背景、选择的方案、关键理由、放弃的替代方案、影响范围和可逆性。已经生效的决策不可静默覆盖；新方案应新增记录，并将旧决策标记为 superseded。

### 3. 领域知识（Domain）

记录模块规则、数据约束、常见故障、修复方法和可复用操作步骤。按主题组织，不按日期组织。

### 4. 工作日志（Log）

记录任务时间线、完成结果、验证情况和待处理事项，仅用于追溯，不作为默认上下文。日志按月组织；兼容宿主平台已有的按日记忆文件。

### 5. 临时上下文（Ephemeral）

当前任务的假设、草稿、未验证想法和一次性命令不得进入长期记忆。任务结束后删除、归档或明确标记过期。

## 三、项目记忆目录

所有平台统一使用项目根目录的 Memory/ 作为记忆目录，不使用任何平台私有目录作为新记忆的写入目标。本项目约定如下：

    Memory/
    ├── MEMORY.md              # 长期记忆索引，启动时优先读取
    ├── PROJECT.md             # 项目稳定事实与全局约束
    ├── ARCHITECTURE.md        # 架构、边界和数据流
    ├── DECISIONS/             # 不可静默覆盖的技术决策
    ├── DOMAINS/               # 按主题维护的领域知识
    ├── LOGS/                  # 按月的轻量工作日志
    └── ARCHIVE/               # 已过期或被替代的内容

需要时才创建上述文件或目录。平台私有目录只作为历史兼容来源读取；新记忆必须写入 Memory/，避免维护两份长期记忆。

迁移历史记忆时，先去重并合并到 Memory/，不要直接复制整目录。迁移完成后，平台私有目录不再作为规范来源。

MEMORY.md 只保留项目定位、架构摘要、关键约束、重要决策索引、主题索引、当前风险和最近更新时间，并保持很短。

## 四、任务完成后的写入流程

任务完成或用户明确要求暂停时，按顺序执行：

1. 收集实际变更、测试/构建结果、相关 Git diff 和最终用户目标。
2. 生成短任务摘要：目标、结果、修改范围和验证方式。
3. 判断是否有长期价值；没有则明确记录“本次无新增长期记忆”。
4. 先搜索相同主题的已有条目，优先更新/合并，禁止无脑追加重复段落。
5. 将稳定事实写入 PROJECT 或 ARCHITECTURE，将决策写入 DECISIONS，将模块知识写入 DOMAINS，将时间线写入 LOGS。
6. 新增或修改主题文档后，同步更新 MEMORY.md 的索引和更新时间。
7. 验证路径、链接、日期、状态和来源，不留下 TODO、占位符或未经说明的猜测。

记忆写入不能阻塞任务交付。写入失败时，保留最小摘要并报告原因，不得伪称写入成功。

## 五、什么内容应该写入

满足以下任一条件时，通常值得沉淀：

- 改变了项目约定、接口、数据格式或目录边界；
- 做出了未来任务需要遵守的技术或产品决策；
- 发现了可能重复出现的故障原因、修复方法或验证方式；
- 形成了经过测试或用户确认的领域结论；
- 发现了明确的风险、兼容性限制或迁移要求；
- 用户表达了稳定的偏好、验收标准或禁止事项。

默认不写入：

- 完整对话、完整命令输出和逐步思维过程；
- 可以直接从 Git diff 或当前代码得到的细节；
- 仅对当前任务有效的草稿、猜测和临时变量；
- 密钥、令牌、个人隐私和其他敏感信息；
- 没有来源、验证或用户确认的事实。

## 六、写入格式

长期条目尽量使用以下元数据，便于检索、审查和过期处理：

    id: memory-YYYYMMDD-short-name
    type: stable | decision | domain | log | ephemeral
    status: active | superseded | deprecated | uncertain
    confidence: verified | user-confirmed | inferred
    source: path, commit, test, or user message
    updated: YYYY-MM-DD
    review_after: YYYY-MM-DD
    tags: [topic, module]

正文只写结论、适用范围、依据和必要示例。单条记忆原则上控制在 3–8 行；超过长度时拆成主题文档或决策记录，并在索引中保留入口。

任务摘要使用以下最小结构：

    ## [日期] [任务名称]
    - 目标：
    - 结果：
    - 关键决策：
    - 变更范围：
    - 验证：
    - 新增/更新记忆：
    - 未解决风险：

## 七、去重、压缩与过期

- 写入前按主题、标签和关键词搜索；同一事实只保留一个规范条目。
- 新事实合并到已有条目并更新 updated，不复制粘贴出第二份版本。
- 每周或累计约 20 个任务后，把重复日志压缩为稳定结论。
- 临时任务记录默认 30–90 天后复查；过期内容移入 ARCHIVE 或删除。
- 被新决策替代的旧文档保留原文，但标记 superseded 并指向新文档。
- MEMORY.md 过大时只保留摘要和索引，把细节下沉到主题文档。

## 八、启动时的读取顺序

接手新任务时，不要一次性加载所有历史内容：

1. MEMORY.md；
2. 与当前任务直接相关的 PROJECT、ARCHITECTURE 或主题文档；
3. 相关 DECISIONS；
4. 必要时再读取最近日志、归档和 Git 历史。

按当前任务检索，避免把无关记忆注入上下文。

## 九、安全与协作边界

- 不记录密钥、令牌、用户隐私或完整环境变量。
- 不把未经验证的推断写成确定事实；使用 status: uncertain 并附验证计划。
- 不覆盖用户未提交的修改；写入前先检查工作区状态。
- 记忆变更应与对应任务一起提交，除非用户明确要求不提交或平台禁止提交。
- 规则与用户当前明确要求冲突时，以用户要求为准，并在任务摘要中记录例外。
- 自动写入失败、冲突或无法判断归属时，停止扩散，保留最小摘要并报告问题。

## 十、完成判定

任务交付前确认：

- 是否产生了未来可复用的事实、决策或风险？
- 它被写入了哪一层记忆，是否更新了索引？
- 是否有来源、状态和验证依据？
- 是否产生重复、过时、敏感或无关内容？

若没有新的长期信息，也应明确记录“本次无新增长期记忆”，不要制造无价值记录。
