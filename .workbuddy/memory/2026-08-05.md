## 后端架构重构 — 代码探查 + 目标方案
- 现状（As-Is）：Vite 静态 SPA + Supabase(PostgREST)，前端用 `@supabase/supabase-js` + 浏览器 anon key 直连库；无独立应用服务层。
- 痛点证据：
  - P1 整库题库/试卷打包进前端 bundle：src/data/examPapers.js(404KB)/questions.js(211KB)/courses.js(44KB)/theoryContents.js(30KB)，由 scripts/fetch-from-supabase.js 构建期写死。
  - P3 内容表 RLS `USING(true)`（supabase-schema.sql 260-283 行）含 answer/solution 字段对匿名全可读 → 考试数据泄露风险。
  - P2/P4 业务逻辑(admin CRUD、wrong_book 状态机、sync 合并)都在浏览器；anon key 进前端，数据模型全暴露。
  - P5 无 Redis/KV 缓存；practice-data.js 仅 memCache+localStorage(1h)。
- 目标（To-Be）：保留 Supabase 作数据/身份底座，新增**无状态 BFF/API Gateway**（Hono/Fastify，CloudBase 函数/容器，自动扩缩），分流 Content API(读多·缓存·隐藏答案) 与 User/Write API(鉴权·限流)；Redis 缓存 + 边缘 CDN；答案经 gated 接口按需返回（复用 answer_reveal 字段）。
- 交付物：backend-architecture-redesign.md（含 As-Is 诊断表、目标架构图、API 示例、SQL 安全补丁、3 阶段迁移计划、需确认 4 项）。
- 待用户拍板：BFF 技术栈、部署目标、Phase 0 安全止血是否立即做、是否落地 Phase 1 脚手架。

## 决策落地：BFF = Hono + Cloudflare Workers
- 用户拍板：Phase 1 用 **Hono** 写 BFF，部署目标改为 **Cloudflare Workers**（边缘运行时，自带全球 CDN，非原方案的 CloudBase）。
- 已交付可运行脚手架：`CourseCore/bff/`（package.json / wrangler.toml / tsconfig.json / .dev.vars.example / README.md）。
- 源码：`src/index.ts`(入口+中间件装配) / `src/env.ts`(Bindings 类型) / `src/lib/supabase.ts`(极简 PostgREST fetch 客户端，service_role 仅服务端) / `src/middleware/{security,cache,rateLimit}.ts` / `src/routes/{health,content}.ts`。
- Content API（Phase 1 只读）：`GET /api/v1/papers`(列表·分页·subject/school/term 过滤) / `/papers/:id`(含 sections+questions 嵌套) / `/papers/:id/questions`(分页) / `/questions/:id`(单题) / `POST /questions/:id/reveal`(501 占位，Phase 2 判分接口)。
- **关键安全点**：所有查询默认字段投影**剔除 answer/answers/solution/test_string**，从根上堵住 P3 泄露；service_role key 仅存 Worker 密钥，浏览器不再持有 anon key。
- 缓存：`caches.default` 边缘缓存(默认 300s, SWR)，内容更新后 Phase 2 用 webhook purge。
- 限流：KV 滑动窗口(120/60s)，未绑 KV 时优雅降级。CORS 已开 `/api/*`。
- 验证：`npm install` 成功，`tsc --noEmit` 通过，`wrangler deploy --dry-run` 打包成功(94KB/gzip 23KB)。
- 下一步：用户填 `.dev.vars` + `wrangler secret put SUPABASE_SERVICE_ROLE_KEY` 后 `npm run deploy`；前端把直连 Supabase 的读改调 BFF；迁移完成后收窄 Supabase `anon` 权限(Phase 0)。
- 注意：wrangler 版本 3.114(有 4.x 提醒)，dry-run 可用的；部署需用户自己的 CF 账号。

## 部署形态澄清（用户补充）
- 用户**前端 SPA 已部署在 Cloudflare Pages**（不是 Workers）。所以 BFF 更优做法是做成 **Pages Function** 与前端同域（xxx.pages.dev/api/*），免 CORS、一次部署。
- 当前 `bff/` 脚手架是**独立 Worker 形态**（`wrangler.toml` main=src/index.ts）。若要转 Pages Function，需改造为 `functions/` 目录 + Hono pages adapter（`hono/cloudflare-pages`），KV/密钥绑定配置位置略有不同（dashboard 或 wrangler.toml 的 pages 段）。
- 两者运行时完全一样（都是 Workers runtime），代码用的 `caches.default`/`executionCtx`/KV 在两种形态都能跑。
- 计费：免费额度内不花钱（Workers 免费 10万次请求/天，Pages 另有免费额度）；付费档(Workers ~$5/月起)按"请求数 + CPU 毫秒"计费。本项目流量小，基本永远在免费额度内。

## BFF 改造为 Pages Function 同域部署（已落地）
- 结论：把 `bff/` 从独立 Worker 形态**改造成 Pages Functions 同域形态**，同时保留 Worker 入口作为可选项（双形态共用同一份 `bff/src/app.ts` Hono 实例，业务逻辑只写一份）。
- 根目录新增：`functions/api/[[route]].ts`（Pages 入口，`import { handle } from 'hono/cloudflare-pages'` 包裹 app）+ 根 `wrangler.toml`（`pages_build_output_dir = "dist"`，即 Vite 构建产物）+ 根 `.dev.vars.example`（已在 .gitignore 追加 `.dev.vars`）。
- `bff/src/index.ts` 改为纯 Worker 入口（`export default app`）；`bff/wrangler.toml` 标注为可选独立 Worker 配置。
- 关键约束：Pages 函数打包时从 `functions/` 位置向上解析 node_modules，故 `hono` 必须装在**根目录**（已 `npm install hono` 到根 package.json，云端 git 构建才能解析）。`supabase.ts` 是纯 fetch 实现、无外部依赖。
- 验证：`bff` 的 `tsc --noEmit` 通过；用 esbuild 跨目录打包 `functions/api/[[route]].ts` 成功(84.4KB, exit 0)，证明跨目录相对导入 + hono 解析正常。
- 部署命令（Pages）：`npx wrangler login` → `npx wrangler pages secret put SUPABASE_SERVICE_ROLE_KEY` → `npx wrangler pages deploy dist`。前端迁移后读 `/api/v1/...` 同域即可，免 CORS。
- SPA 深链提示：若用 history 路由且需回退 index.html，在 `public/_redirects` 加 `/* /index.html 200`（/api/* 由函数优先处理不受影响）。当前站点疑似 hash 路由则无需。
